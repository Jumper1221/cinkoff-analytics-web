## 1. Ответы-предложения на 4 вопроса §11 AUTH_DESIGN.md

### В1. Схема «Access 15 мин в памяти + Refresh 7/30 сут в HttpOnly-куке, ротация + reuse detection»

**Предложение: ДА, утверждаю как есть.**

- *Почему:* единственная схема из §2, закрывающая все чек-пункты §8 одновременно (короткий
  access, кука вместо localStorage, ротация по RFC 9700 §4.14). Альтернатива «обе куки»
  (access тоже в куке) экономит ~40 строк фронта, но возвращает длинный(t=7 сут) Credentials
  в каждый запрос и лишает смысла деление access/refresh — несогласен с ней.
- *Цена:* перехватчик и single-flight-refresh в `api/client.ts` (~40 строк), стор + гарда
  (~60), сами эндпоинты. Плюс операционная цена: F5 через 15+ мин молча делает
  refresh-запрос — в логах появится «лишний» POST /api/auth/refresh на каждый вход.
- *Нюанс внедрения, не отражённый в дизайне:* у нас в `client.ts:9-23` уже есть
  retry-цикл `retries=2` с бэкоффом 400/800 мс. Если 401 оставить внутри этого цикла,
  один несчастный 401 породит до 3 последовательных refresh-запросов (рассинхрон ротации).
  → 401 исключается из общего retry-цикла: один refresh (single-flight для параллельных
  запросов) → один повтор. Это фикс-требование к шагу 4, см. §3.3.

### В2. Пароль — Argon2id-хэш в ENV (генерится скриптом)

**Предложение: ДА, но только с уже заложенным фоллбеком на голый `WEB_PASSWORD`.**

- *Почему:* OWASP-стандарт, генерация одноразовая, стоимость нулевая. Фоллбек (§3 дизайна:
  пустой `WEB_PASSWORD_HASH` → берётся `WEB_PASSWORD` строкой) — обязателен: это наша
  точка отката и теневой режим.
- *Цена:* +1 зависимость `argon2-cffi` (компилируется быстро, wheel-ы есть), +1 скрипт
  `hashgen`, +память: verify Argon2id ~50–100 мс и ~1–2 МБ на вызов — раз в сессию, неважно.
- *Нюанс:* оба варианта должны быть покрыты тестами (хэш задан / только `WEB_PASSWORD`) —
  иначе «временный» фоллбек гниёт и станет постоянным сюрпризом.

### В3. Reuse detection → отзыв всей семьи при повторном использовании refresh

**Предложение: ДА, но с двумя дешёвыми демпферами (в дизайне их нет — мой главный аргумент-поправка).**

- *Почему да:* стандарт, единственный способ заметить перехват без sender-constrained (mTLS-стиль) токенов.
- *Грабля-1 (реальный наш сценарий):* перехватчик 401→refresh в SPA при дозагрузке вкладки
  стреляет **параллельно из 2+ упавших запросов** — оба читают одну и ту же куку, оба
  преследуют ротацию, второй приходит со «сгоревшим» → законная гонка наказывается отзывом
  всей семьи и вылогином. Лечится на клиенте (single-flight, В1) **и** на сервере.
- *Грабля-2 — **не согласен с буквальной формулировкой §4.2/В3** («пришёл сгоревший второй
  раз → отзыв»)*: предлагаю **grace-окно 30 сек** на сервере: повторное использование в
  30 с после ротации → обычный 401 (`invalid_refresh` + обнуление куки) **без** отзыва
  семьи. Это одна строка условия SQL (`AND now() - revoked_at > interval '30 seconds'`)
  и убирает весь класс «ложных перехватов» при параллельных 401- retriesaх, если клиент
  вдруг не успел (вторая вкладка, гонка до перехватчика).
- *Цена:* +1 условие в запросе +1 поле-логика; иначе — периодические «непонятные
  разлогины», которые мы не сможем объяснить в единственном-пользовательском проде.

### В4. Хранилище refresh — таблица в нашем Postgres

**Предложение: ДА. Альтернативы не рассматриваю всерьёз.**

- *Почему:* reuse detection и отзыв невозможны без серверного состояния. In-память — до
  первого рестарта; у нас контейнер пересобирается на каждый деплой бэка → вылогин при
  каждом деплое. ФС-файл — второй источник истины рядом с Postgres, который и так здесь.
  Таблица из §4.2 (7 колонок) — минимально достаточная; MySQL/Redis — новый сервис ради
  1 (одной) таблицы.
- *Цена:* одна идемпотентная миграция (DDL в §4) + правило «чистка при refresh»
  (там же). Нагрузка: 1 пользователь, единицы ротаций в час — Postgres не заметит.
- *Нюанс деплоя (учтено в §4):* миграции у нас накатываются вручную через
  `docker exec … psql`; `db.py:34` применяет `schema.sql` при старте парсера/fetcher-контейнера,
  но не бэка → ручной прогон обязателен, DDL обязан быть IF NOT EXISTS.

**Сводка «где не согласен с документом» (все — к благу, см. В1/В3 + §5):**
1. Grace 30 с на reuse (В3) — иначе ложные отзывы при гонке.
2. 401-обработка во фронте должна быть вне существующего retry-цикла `client.ts` (В1).
3. Мидлварь не «переписываем» (§4.4), а делаем **единый auth-mw с 3 режимами по ENV**
   (обе переменные пусты → как сегодня; только `WEB_PASSWORD` → старое basic; задан
   `WEB_JWT_SECRET` → JWT с dual-accept). Это и есть теневой режим, и это же — точка отката
   (§3.2). Сохранение Basic-ветки как фоллбека — бессрочно.
4. Редирект легаси-SPA при 401 — на **`/v2/login?from=…`**, а не на `/login` (§6 дизайна):
   `/login` не существует ни в nginx (он уйдёт в `location /` → бэк → 404: у бэка есть
   только `/`, `/legacy`, `/v2/*`), ни в vue-router (база `/v2/`). См. риск R2.
5. Dual-accept-кука (§2): «та же кука, но с `Path=/`» — формулировка невыполнима: кука с
   `Path=/api/auth/refresh` и кука с `Path=/` — это **два разных** cookie. Исправлено в §3.3:
   при логин/refresh ставятся **два Set-Cookie с одним значением**: узкая для refresh + широкая
   для CSV-ссылок.

## 4. БД: DDL миграции + применение

DDL (идентичен §4.2 AUTH_DESIGN.md, чтобы не плодить расходники; добавить в конец
`app/schema.sql` — В ОБЕ копии: `cinkoff_parser/app/schema.sql` и `.backend-src/app/schema.sql`):

```sql
-- ── Авторизация: refresh-токены (JWT_IMPL_PLAN.md; износ: ссерверная ротация + reuse detection) ──
CREATE TABLE IF NOT EXISTS auth_refresh_tokens (
  id          bigserial PRIMARY KEY,
  token_hash  text NOT NULL UNIQUE,      -- SHA-256(opaque-токен + WEB_REFRESH_SECRET-пеппер)
  issued_at   timestamptz NOT NULL DEFAULT now(),
  expires_at  timestamptz NOT NULL,
  revoked_at  timestamptz,               -- NULL = жив; при ротации заполняем
  replaced_by bigint,                    -- id следующего в цепочке (отладка)
  client_info text                       -- первые 120 символов User-Agent, не секрет
);
CREATE INDEX IF NOT EXISTS idx_auth_rt_expires ON auth_refresh_tokens(expires_at);
```

Grace-поправка (В3): условие reuse-проверки в коде —
`revoked_at IS NOT NULL AND now() - revoked_at > interval '30 seconds'` → обычная 401;
внутри окна → 401 без отзыва семьи. Меняет ТОЛЬКО условие в WHERE, не DDL.

**Применение (миграции у нас вручную; `db.py:34` гоняет schema.sql только на старте
парсер/fetcher-контейнеров, бэк-контейнер — никогда):**

```bash
# 1) узнаём фактическое имя контейнера БД (проект-композа парсера):
docker ps --format '{{.Names}}' | grep -i db
# 2) накатываем (идемпотентно — можно запускать многократно):
docker exec -i cinkoff_parser-db-1 psql -U orders -d orders <<'SQL'
<текст DDL из блока выше>
SQL
# 3) проверка:
docker exec -i cinkoff_parser-db-1 psql -U orders -d orders -c '\d auth_refresh_tokens'
```

Повторный запуск всего `schema.sql` целиком — безопасен (весь файл — IF NOT EXISTS, как
и заявлено в его шапке). Если отдельные таблички кто-то руками мутировал — DDL-блок выше
их не касается.

**Чистка:** при каждом успешном refresh —
`DELETE FROM auth_refresh_tokens WHERE expires_at < now() - interval '60 days'` (без крона).
Ревiю-в-два-места не забывать: SELECT+UPDATE+DELETE — одна-две往返, вне пула-конкуренции
(один процесс-бэк, §4.2 дизайна).

## 5. Риски/грабли, специфичные для НАШЕГО деплоя

- **R1. Бэк-код в двух копиях (`.backend-src` — зеркало парсер-`app/`).** Деплоится в прод
  только копия из `.backend-src` (контекст сборки `docker-compose.yml:18-19`), а тесты
  гоняются по парсер-оригиналу. Забыл скопировать → «на моей машине зелёно, в проде
  ImportNotFoundError». правило: шаг бэка всегда = 2 обязательных места +diff обеих папок
  перед деплоем (`diff -rq ../cinkoff_parser/app .backend-src/app` — сегодня они равны,
  и это надо сохранять). Сюда же: легаси-контейнер `cinkoff_parser-web-1` (его обновляет
  `deploy-v2.sh`) — вторая инкарнация; подтверждить на шаге 0, кто из них слушает 8010,
  иначе «включили секрет в одном, работает другой».
- **R2. nginx-маршруты: `/v2/*` — статика, `/` — его index.html, всё прочее — на бэк.**
  Следствие: `/login` в лоб не существует: nginx утащит его в `location /` → бэк → 404.
  Решение: легаси-редирект и фронт-гварда используют `/v2/login?from=…` (истина — В4-п.4);
  опционально 301-строка в nginx.conf. Плюс помніть: `/api/*` проксируется без подрезки
  заголовков — `Authorization` доходит как есть; `X-Real-IP` есть только у `location /`
  (:41) → для rate-limit-по-IP в `location /api/` добавить `proxy_set_header X-Real-IP $remote_addr;`
  (иначе лимит считаем по пустоте; одна строка — единственная оправданная правка nginx).
- **R3. CSV-двойной accept + cp1251.** Экспорт — двоичный cp1251-буфер через
  `StreamingResponse` (web_orders.py:126). Ломать его нельзя: значит, dual-accept делает
  ТОЛЬКО мидлварь (accept-ветка), роут — неприкосновенный; тест-кейсы (§3.3) обязаны
  проверять `charset=cp1251` и «тот же байт-поток» (golden-снимок CSV до/после — шаг 0/6).
  Если новая широкая кука забудется — сломается выгрузка легаси (найти ДО включения, шаг 3).
- **R4. HTTP без HTTPS (LAN).** Всё по HTTP: токены и куки — plaintext на провода.
  Осознанно (решение ACCEPT_DESIGN §8): для LAN-аналитики — ок; поставить
  `WEB_COOKIE_SECURE=0` и НЕ ловиться на «а давайте сразу HTTPS» (это отдельный проект:
  сертификаты на LAN-IP, тремор, офф-лайн-обновления). Контроль-тумблер уже есть:
  при выходе в интернет → `WEB_COOKIE_SECURE=1` + один-два часа на реальный HTTPS-фронт.
- **R5. Порядок мидлварей Starlette.** Последний добавленный — внешний (первый на входе).
  Сейчас: GZip(28) → cache_control(31) → basic(65) — значит вход: basic → cache_control → GZip.
  Новый `auth_mw` добавляем НИЖЕ по файлу (после basic) → он внешний: 401 отдаётся ДО
  лишних слоёв, а basic-ветка в «секретном» режиме просто не вызывается для /api/*.
  Если добавить ДО basic по коду — получим двойную авторизацию (JWT-пропустил, basic-нет
  → 401-от-пароля-домучит) — явно проверить в шаге 2 тестом «Bearer-запрос с ВЫКЛ-паролем → 200».
- **R6. Refresh-гонка в собственном фронте.** Устраняется однажды: single-flight в
  `client.ts` + grace 30 с на бэке (В1/В3). Без этого — «случайные» вылогины при открытых
  2-3 вкладках. Тест (шаг 2, класс TestAuth): 2 параллельных refresh с одной куки →
  один 200, второй — 401, семья жива (grace), не отозвана.
- **R7. Тестовая-инфра.** Контракт-тесты — без БД: их сила (скорость) и ограничение.
  Всё новое, требующее БД (ротация/revocation) — в disposable-PG-тесты по конвенции
  парсера; НЕ тащить фикстурные превращения в контракт-тесты. И: фикстура патчит
  `web_auth.q` на месте вызова (по паттерну :288-306), потому что импорт `from web_common
  import q` создаёт модульную ссылку — общий-патч `web_common` не помог бы.
- **R8. Разнобой порт-ов/стеков в доках.** Makefile этого репо упоминает 8011, compose —
  8010:8080, AUTH_DESIGN — 8010. На шаге 0 зафиксировать в README единственную истину
  (прод-вход = 8010), чтобы шаг 6 не палить по неправильному порту.
