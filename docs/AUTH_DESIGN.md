# Авторизация сервиса аналитики — JWT (production-подход)

Статус: **НА УТВЕРЖДЕНИЕ** (2026-09-25, версия 2 — по мировым практикам; заменяет версию 1 про подписанную куку).
Источники: OWASP Cheat Sheets (JSON Web Token, Authentication, Session Management), RFC 9700 (OAuth 2.0 Security BCP), практики «FastAPI in Production».

Скоуп: только сервис аналитики `http://192.168.1.77:8010` (порт не менять). Exam-prep (8020) — вне скоупа.
2FA не нужна (решение Михаила). Достаточно JWT + refresh-токен.

## 1. Что защищаем

- `/api/*` — 38 JSON-эндпоинтов + `/api/sync` (запуск синка!) + CSV-экспорт.
- `/v2/*` — SPA v2 (Vue3), `/legacy` + `/static/*` — легаси-SPA.
- `/healthz` — открыт (ничего не раскрывает, нужен для проверок).

Данные приватные (заказы, контрагенты, выручка 2019–2026). Сейчас всё открыто
(`WEB_PASSWORD` не задан). Когда светим сервис в интернет — авторизация обязательна.

## 2. Выбранная схема: Access + Refresh (стандарт прод-SPA, 2026)

| Токен | Что | Где живёт | Транспорт |
|---|---|---|---|
| **Access** | JWT (HS256), TTL **15 мин** | память JS (Pinia-стор), НЕ localStorage | `Authorization: Bearer <jwt>` |
| **Refresh** | непрозрачный, TTL **7 дней** (30 при «запомнить») | HttpOnly-кука | только на `POST /api/auth/refresh` |

Почему так (каждый пункт — прямая рекомендация, не вкус):
- **Access короткий** → украденный быстро умирает. «Access на 24 часа» — типовая ошибка.
- **Refresh — HttpOnly-кука, не localStorage** → недоступен XSS (OWASP Session Management
  Cheat Sheet прямо требует не хранить токены в storage). У нас всё same-origin, поэтому
  CORS-проблем нет в принципе.
- **Кука узкая** (`Path=/api/auth/refresh`) → уходит только на один эндпоинт.
- **Ротация refresh**: при каждом использовании старый погашен, выдан новый. **Reuse
  detection**: пришёл «сгоревший» второй раз → значит, был перехват → отзыв всей семьи.
  Это требование RFC 9700 §4.14 (refresh-токены публичных клиентов: sender-constrained
  ИЛИ ротация; для нас — ротация с детекцией).
- **Logout** = отзыв семьи + сброс куки. Access доживает свои 15 мин — осознанный
  трейд-офф stateless-JWT; мгновенный отзыв (denylist по `jti`) — пункт roadmap §10.

### Почему HS256, а не RS256/JWKS

RS256+JWKS нужны, когда несколько сервисов выпускают/проверяют токены. У нас один издатель
и один потребитель (наш же бэк) → HS256 с 256-битным секретом достаточен. Ротация ключа =
смена ENV + рестарт (редкая операция). Валидация: `jwt.decode(..., algorithms=["HS256"],
issuer=..., audience=...)` — алгоритм зафиксирован (закрывает «algorithm confusion» OWASP).

### CSV-экспорт и `<a href>`: dual-accept

`<a href>`-ссылки не умеют ставить заголовки. Прод-решение: экспортные эндпоинты принимают
И `Authorization: Bearer`, И валидную сессионную куку (та же кука, но с `Path=/`). Фронт и
легаси не переписываем, ссылки качаются как раньше. Помечается комментарием в коде.

## 3. Аккаунты и секреты (ENV)

Один пользователь (Михаил) — таблица-пользователей избыточна, но пароль — по-продакшену:

- `WEB_JWT_SECRET` — 64 hex-символа (`openssl rand -hex 32`), подпись access-JWT.
- `WEB_USER` — логин, дефолт `m` (снимаем хардкод со старого middleware).
- `WEB_PASSWORD_HASH` — **Argon2id-хэш** пароля (OWASP-стандарт; не голый пароль).
  Генерится один раз: `python -m app.auth.hashgen "пароль"`. Фоллбек: если пусто — берётся
  устаревший `WEB_PASSWORD` строкой (совместимость с текущим порядком, откат не ломается).
- `WEB_COOKIE_SECURE` — пока 0 (HTTP LAN); при HTTPS — 1, кука получает флаг Secure.
- Значения — в `.env` проекта, в git не попадают (правило репо). `.env.example` — заглушки.

Смена/восстановление пароля: пересоздать хэш + рестарт контейнера. Ролей нет.

## 4. Протокол (эндпоинты + мидлварь)

### 4.1 Эндпоинты

- `POST /api/auth/login` ← JSON `{user, password, remember}` →
  200: `{"access_token": "...", "token_type": "bearer"}` +
  `Set-Cookie: cinkoff_rt=<opaque>; HttpOnly; SameSite=Lax; Secure(при HTTPS); Path=/api/auth/refresh; Max-Age=<7|30 сут>`
  - Проверка пароля: Argon2-verify (constant-time), сравнения — `hmac.compare_digest`.
  - Неудача: 401 `{"detail":"bad_credentials"}` + фиксированная пауза 0.4с.
  - **Rate limit: 5/мин на IP** (прод-практика; пока uvicorn-однопроцессный — in-process
    счётчик; при переезде на несколько воркеров — Redis, помечено TODO).
  - Аудит-лог: `login ok user=X ip=Y` (в обычный uvicorn-лог, без паролей/токенов).
- `POST /api/auth/refresh` — кука `cinkoff_rt`; проверка хэша в БД (§4.2):
  - живой и не «сгоревший» → **ротация**: новый refresh (кука) + новый access (тело ответа);
  - «сгоревший» пришёл повторно → 401 `{"detail":"token_used"}` + **отзыв всей семьи**;
  - невалидный/просроченный → 401 `{"detail":"invalid_refresh"}`, кука обнуляется.
- `POST /api/auth/logout` — отзывает свою семью, сбрасывает куку. 200 всегда (идемпотентно).
- `GET /api/auth/me` ← Bearer → `{"user":"m"}` | 401 (гарда фронта).

Дополнительно на `/api/auth/*` (мутирующие) — проверка `Origin`/`Referer`: три строки,
закрывает CSRF-хвост при кука-транспорте (same-origin + SameSite=Lax уже закрывают большую
часть, это добивка).

### 4.2 Хранение refresh-токенов: таблица в Postgres

Только серверное хранилище даёт reuse detection и отзыв:

```sql
CREATE TABLE IF NOT EXISTS auth_refresh_tokens (
  id          bigserial PRIMARY KEY,
  token_hash  text NOT NULL UNIQUE,      -- SHA-256(opaque-токен + WEB_REFRESH_SECRET-пеппер)
  issued_at   timestamptz NOT NULL DEFAULT now(),
  expires_at  timestamptz NOT NULL,
  revoked_at  timestamptz,               -- NULL = жив; при ротации заполняем
  replaced_by bigint,                    -- id следующего в цепочке (отладка)
  client_info text                       -- первые 120 символов User-Agent, не секрет
);
CREATE INDEX IF NOT EXISTS idx_auth_rt_expires ON auth_refresh_tokens(expires_at);
```

- Идемпотентная миграция (`IF NOT EXISTS`) — по правилу репо: боевые данные не трогаем.
- Токен: `secrets.token_urlsafe(32)` — 256 бит энтропии; в БД только хэш.
- Чистка: при каждом refresh — `DELETE WHERE expires_at < now() - interval '60 days'`
  (одна строка, без крона).
- Схема БД, замечание: у нас один контейнер-бэк — конкурентных ротаций от двух процессов
  не будет; при масштабировании — `SELECT ... FOR UPDATE` на строку.

### 4.3 Access-JWT: точная спека

```jsonc
{
  "sub": "m",                 // логин
  "type": "access",           // отличать от refresh — проверка обязательна
  "iat": 1758800000,
  "exp": 1758800900,          // +15 мин
  "jti": "<uuid4>",           // для будущего denylist (пишем, пока не проверяем)
  "iss": "cinkoff-analytics",
  "aud": "cinkoff-analytics"
}
```

- Библиотека: **PyJWT** (поддерживаемый стандарт; умерший python-jose не берём).
  Деп-зависимость: `PyJWT>=2.9`.
- Payload без ролей/пермиссий — лишнее (один пользователь).

### 4.4 Мидлварь (переписываем существующую)

- Публичные пути: `/api/auth/*`, `/healthz`, ассеты: `/static/*`, `/static_v2/*`,
  `/v2/assets/*`, `/favicon.ico`.
- Прочие `/api/*`: проверка `Authorization: Bearer` (+ `type=access`, `iss`, `aud`, `exp`);
  нет/битый → 401 JSON `{"detail":"unauthorized"}` + `WWW-Authenticate: Bearer`.
- SPA-пути (`/`, `/v2/*`, `/legacy`) без токена → отдаются как есть (SPA загрузится, гарда
  решит по 401 от `/api/auth/me`). Сервер-редиректы HTML-роутов не нужны — стандарт SPA.
- `/api/orders/export` — dual-accept (Bearer ИЛИ кука, §2).

## 5. Фронт v2 (Vue3 + TS)

- `stores/auth.ts` (Pinia): `accessToken` (Ref — только память), `user`, `login()`,
  `logout()`, `tryRefresh()`, `ensureLoaded()`.
- `LoginView.vue` + роут `/login`: логин, пароль, «запомнить на этом устройстве» (30 дней),
  Enter-сабмит, ошибка «Неверный логин или пароль», кнопка заблокирована на 0.4с.
  После успеха — возврат на `?from=`-маршрут.
- Роут-гарда `beforeEach`: однократный `GET /api/auth/me` (кэш в сторе); 401 →
  `/login?from=<текущий-путь>`. Но сначала **тихий refresh**: кука уже может быть жива —
  тогда продолжаем как залогиненные (F5 не разлогинивает).
- Перехватчик в `api/client.ts request()`: 401 → одна попытка `POST /api/auth/refresh` →
  повтор исходного запроса с новым токеном; не вышло → `/login?from=…`
  (одна-попытка-политика — против зацикливания refresh-петли).
- В шапке: `m · Выйти` (POST logout → кука сброшена → на /login). Видно только залогиненным.

## 6. Легаси-SPA

Одна правка в `src/js/common.js`: обёртка поверх точки запросов — 401 →
`location = '/login?from=' + encodeURIComponent(location.hash)`.
CSV-ссылки легаси работают как раньше (dual-accept, §2).

## 9. Этапы внедрения (после утверждения; малые шаги — как принято)

1. **Бэк-фундамент**: зависимости; `app/auth.py` (хэши, токены, ротация, ревокация);
   таблица (идемпотентно); юнит-тесты (disposable-PG, как принято в парсере).
2. **Бэк-эндпоинты**: 4 роута + новый мидлварь + dual-accept CSV + rate-limit + аудит-лог.
   Пока без секретов в ENV — поведение прежнее (пусто = всё открыто; не-ломающий деплой).
3. **Фронт v2**: `stores/auth.ts` + `LoginView` + роут-гарда + перехватчик 401→refresh→retry
   + «Выйти». Гейты: `npm run typecheck && npm run test && npm run build` — все три.
4. **Легаси**: 401-обёртка в `common.js` (headless: `/legacy` без куки → редирект на /login).
5. **Прод**: сгенерить секреты/хэш, вписать в .env, `docker compose up -d --build backend`.
   Приёмка: инкогнито → логин-экран; после входа всё работает; CSV качается; F5 не
   разлогинивает; выход → блок; `/api/sync` под токеном; легаси-вьюхи живы; 0 ошибок консоли.
6. **Доки**: README-раздел «Вход» + уроки в скилл.

Оценка: ~300–400 строк суммарно (бэк ~200, фронт ~120, легаси ~15, миграция ~20).
